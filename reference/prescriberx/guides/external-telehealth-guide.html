External Telehealth API

← Back to API reference

Integration surface for 3rd-party telehealth companies that prescribe in their own e-Rx system and route fulfillment through PrescribeRx. Two endpoints to register prescribers + look them up, one to submit fully-formed prescription orders. Webhook subscribers receive status callbacks back as orders progress.

At a glance

EndpointPurposeAbility
POST /api/v1/external-telehealth/providersRegister prescriber (idempotent on NPI+client)external-telehealth:providers:write
GET  /api/v1/external-telehealth/providers/{npi}Look up provider(s) — poll for admin approval stateexternal-telehealth:providers:read
POST /api/v1/external-telehealth/ordersSubmit a fully-formed prescription orderexternal-telehealth:orders:write

The interactive Try-It client for all three endpoints is on the main API reference, under the ExternalTelehealth tag.

1 — How tenancy works

The effective sales-org id resolves from either side of the user identity graph:

effective_sales_org_id = user.sales_organization_id
                       ?? user.client.sales_organization_id

Both token shapes are supported:

Token shapeWhat it can do
Sales-org Submit orders / register providers against any client_id under its sales org. Use this when a 3rd-party telehealth company serves multiple of your clinics.
Client Effectively pinned to its own client_id — the only payload value that resolves to its sales org's client tree. Use this when a single clinic / practice integrates directly.

Cross-tenant client_id → HTTP 403 with: "API user must belong to a sales organization (directly, or via their client)."

2 — Onboarding (one-time)

  1. Your account rep creates either a SalesOrganization (multi-clinic integrator) or a Client (single-clinic) for you, plus an API user.
  2. The rep issues a Sanctum bearer token for that API user with these abilities, which are granted manually (NOT in any default ability set):
    • external-telehealth:providers:write
    • external-telehealth:providers:read
    • external-telehealth:orders:write
    Webhook abilities (webhook:*) are already in the default set for both sales-org and client user types.
  3. Save the token securely — it's not retrievable from our side once issued.
  4. Test against https://demo.prescribe-rx.com first. Production is https://prescribe-rx.com with identical shapes.

Payments & merchant accounts (one-time — required for on-system billing)

If you process the patient's payment on your own gateway (outside PrescribeRx) but want PrescribeRx to handle any future billing on that card — subscription rebills, refills, deferred captures, refunds — you must add that merchant account inside PrescribeRx first. Without it, the transaction you report is recorded audit-only (no merchant attached) and any card you send is stored display-only (not chargeable).

  1. In the PrescribeRx portal as your sales org, go to Settings → Payments → Merchant Accounts and add an account for the same gateway you charge on (authorize_net, stripe, nmi, or square), with that gateway's credentials. Mark it active.
  2. Copy its merchant account UUID.
  3. On each intake you submit, include the payment block with mode: "reference_captured" (or reference_preauth), your merchant_account_id, the transaction details (id + amount), and — to make the card rechargeable — the durable card_token refs from your gateway's vault (e.g. Stripe customer_id + payment_method_id; Auth.Net customer_profile_id + payment_profile_id; NMI customer_vault_id; Square customer_id + card_id). See the payment block on POST /telehealth/intake/unified in the API reference for the full field-by-field contract and a complete example.

The merchant's gateway must match your card_token refs and the account must belong to your org — PrescribeRx validates both and, on a mismatch, records the transaction without a merchant rather than charging the wrong account. Collected payment in person / out of band with no electronic record? Omit payment or use mode: "prepaid".

3 — Register a provider

Every prescriber must exist + be admin-approved before any order can reference them by NPI.

cURL

curl -X POST https://demo.prescribe-rx.com/api/v1/external-telehealth/providers \
  -H "Authorization: Bearer $TOKEN" \
  -H "Accept: application/json" \
  -H "Content-Type: application/json" \
  -d '{
    "client_id": "<your client UUID>",
    "npi": "1234567890",
    "dea": "BX1234567",
    "first_name": "Alex",
    "last_name": "Smith",
    "prefix": "DR",
    "suffix": "MD",
    "designation": "MD",
    "dob": "1980-01-15",
    "gender": 1,
    "email": "alex.smith@example-clinic.com",
    "state_licenses": [
      {"state": "GA", "license_type": "MD", "license_number": "GA-12345", "expiration_date": "2027-01-01"},
      {"state": "FL", "license_type": "MD", "license_number": "FL-67890", "expiration_date": "2027-06-01"}
    ]
  }'

Response codes

StatusMeaning
201New provider registered. data.status = "PENDING". Wait for admin approval before submitting orders.
409A provider with this (npi, client_id) already exists. Response includes the existing data.provider_profile_id.
403The client_id does not belong to your sales org tree.
422Validation error. Check errors[] for field-level details.

Poll for approval

curl https://demo.prescribe-rx.com/api/v1/external-telehealth/providers/1234567890 \
  -H "Authorization: Bearer $TOKEN" \
  -H "Accept: application/json"

Returns an array (same NPI can have multiple rows when the prescriber works at multiple of your clients). Loop until data[].status === "ACTIVE".

4 — Submit an order

Idempotency-Key header is REQUIRED. Any unique string per order (UUID v4 recommended). Re-POSTing the same key within 24h returns the original order as HTTP 200 (not 201). Keys are scoped to the caller's sales org.

cURL — happy path (non-compounded SKU)

curl -X POST https://demo.prescribe-rx.com/api/v1/external-telehealth/orders \
  -H "Authorization: Bearer $TOKEN" \
  -H "Accept: application/json" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{
    "client_id": "<your client UUID>",
    "provider_npi": "1234567890",
    "external_order_id": "ACME-2026-05-14-00042",
    "patient": {
      "first_name": "Jane",
      "last_name": "Doe",
      "email": "jane.doe@example.com",
      "date_of_birth": "1985-03-12",
      "phone": "+15555550100",
      "gender": 2,
      "address": {"line1": "123 Main St", "city": "Atlanta", "state": "GA", "postal_code": "30301"}
    },
    "shipping_address": {"line1": "123 Main St", "city": "Atlanta", "state": "GA", "postal_code": "30301"},
    "prescription": {
      "pdf_base64": "JVBERi0xLjcKJWZha2UgcGRmCg==",
      "signed_at": "2026-05-14T14:00:00Z",
      "signed_by_name": "Dr. Alex Smith, MD"
    },
    "lines": [
      {
        "sku": "GLPSEMA-12-TABLET",
        "quantity": 1,
        "sig": "Take one 12 mg tablet by mouth once weekly",
        "days_supply": 28,
        "dose_amount": "12",
        "dose_unit": "mg",
        "frequency": "weekly",
        "refills": 0
      }
    ]
  }'

Idempotency replay test

Re-send the same payload with the same Idempotency-Key. The second response is HTTP 200 (not 201) and the body matches the original — regardless of what the payload says. No duplicate order is created. Use this to safely retry on network failures.

5 — Response codes

StatusMeaning
201 CreatedOrder accepted, routed to fulfillment. Includes order_id, order_number, prescription_id, prescription_pdf_path.
200 OKIdempotency replay — same key was used within 24h. Body matches the original 201.
404 Not FoundThe NPI isn't registered at this client. Call POST /providers first.
403 ForbiddenProvider exists but is still PENDING admin approval, OR client_id is not in your sales org tree.
422 Unprocessable EntityValidation error: unknown SKU, malformed PDF, missing compounding_reason_slug on a compounded product, NPI doesn't normalize to 10 digits, missing Idempotency-Key header.
401 UnauthorizedMissing / invalid token.

6 — Webhook callbacks

Status updates flow back via the standard webhook subscription system. Subscribe once for your sales-org / client; you'll receive events for every order it owns. See the dedicated Webhooks Guide for HMAC signature verification + retry policy.

Subscribe

curl -X POST https://demo.prescribe-rx.com/api/v1/webhooks \
  -H "Authorization: Bearer $TOKEN" \
  -H "Accept: application/json" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://your-platform.com/webhooks/prescribe-rx",
    "events": [
      "order.placed",
      "order.status_changed",
      "order.cancelled",
      "fulfillment.shipped",
      "fulfillment.delivered",
      "fulfillment.cancelled"
    ],
    "subscriber_type": "sales_organization",
    "subscriber_id": "<your sales-org UUID>"
  }'

Use "subscriber_type": "client" + your client UUID instead for client-token integrators.

The response's data.secret (starts with whsec_) signs every outgoing payload — store it securely. Outgoing requests carry the signature in X-PrescribeRx-Signature (HMAC-SHA256 of the raw body).

Events you'll receive (External Telehealth orders)

EventWhenPayload key
order.placedImmediately after our 201 to your POST /ordersorder_id, order_number, total_amount, external_order_id
order.status_changedworkflow_status transitionsold_status, new_status, external_order_id
order.cancelledAdmin or system cancelsreason, cancelled_at, external_order_id
fulfillment.shippedFC reports the order shippedtracking_number, tracking_url, carrier, shipped_at, external_order_id
fulfillment.deliveredCarrier reports deliveredtracking_number, delivered_at, external_order_id
fulfillment.cancelledFC cancellation (rare; usually inventory)reason, cancelled_at, external_order_id

Every payload includes your supplied data.external_order_id when the order originated from this API — use it to correlate with your internal records.

7 — Troubleshooting

SymptomLikely causeFix
401 UnauthorizedToken expired or wrong headerReissue. Header is Authorization: Bearer <token> with the full <id>|<random> string.
403 "missing ability"Token issued without the right abilitiesAsk your rep to re-issue with external-telehealth:* abilities.
403 "client_id does not belong to your sales organization"Wrong client UUID or cross-tenantVerify the UUID against the list your rep provided. Client-token integrators must use their own client_id.
404 "No provider found for this NPI at the given client"Not yet registered, OR registered at a different clientCall POST /providers first, or fix the client_id in your payload.
403 "Provider is registered but not yet ACTIVE"Admin hasn't approved yetWait; poll GET /providers/{npi}.
422 "Unknown product SKU"SKU isn't in our catalog or was retiredAsk your rep for the current SKU list. Case-sensitive.
422 "is compounded and requires `compounding_reason_slug`"Compounded product without a slugAdd compounding_reason_slug to the line.
422 "Header `Idempotency-Key` is required"Forgot the headerAdd Idempotency-Key: <uuid> to every order POST.
422 "prescription.pdf_base64 does not contain a valid PDF"Decoded bytes don't start with %PDF-Re-export from your e-Rx. Common cause: double base64 encoding, or sending raw text.
200 OK instead of 201 on a fresh POSTReused an Idempotency-Key from a prior orderGenerate a fresh UUID per distinct order.
Need a sandbox-ready token? The sandbox tokens panel on the main API reference auto-rotates one every 12h. Look for the SALESORGANIZATION entry, or ask an admin to issue an explicit External Telehealth token via tinker (procedure documented internally).
