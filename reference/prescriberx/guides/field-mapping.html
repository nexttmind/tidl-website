API Field Mapping

← Back to API reference

Every POST /api/v1/telehealth/intake/unified payload field maps to one or more destinations on the server: a column on encounters / patient_charts, a tier-1/2/3 JSON storage column, an encounter_intake_answers row, or an upserted chart-side record (medication / allergy / condition / vital / address / document). This page documents that mapping so integrators can predict — without reading source code — exactly where their data lands.

Storage tiers (legend below). tier 1 Strict — core demographics on patient/chart. Validation always required. tier 2 Flexible — vitals + medical history. Validated but not strictly typed. tier 3 Lax — encounter-specific Q&A. Provider-reviewable. chart-sync IntakeAnswerRouter mirrors this to chart-side rows. document Persists as a patient_documents row.

One of three shapes; the controller normalizes to two addresses rows on the chart (one SHIPPING default, one BILLING default).

ShapeWhat it does

Sub-fields on every address shape: street, street2, city, state (2-letter), zip, country (2-letter, default US).

Medical history (tier 2 + chart-sync)

Three string arrays, each routed to chart-side rows via the typeahead-aware IntakeAnswerRouter. Strings are matched against terminology_* tables — unmatched strings are persisted as free-text on the chart row. tier 2chart-sync

API fieldDestinationNotes
medical_history.allergies[]patient_allergies (one row per string)
+ tier2_medical_history.allergies		Empty / "None" / "NKDA" results in a row with has_no_allergies=true.
medical_history.medications[]patient_medications (one row per string)
+ tier2_medical_history.medications		String-only — for structured dose/frequency, use the /me/patient/medications endpoint instead.
medical_history.conditions[]patient_conditions (one row per string)
+ tier2_medical_history.conditions		Matches terminology_conditions by display name; unmatched → free-text row.
How chart sync works (deeper dive)

After the encounter is created, IntakeAnswerRouter::route() walks medical_history.* and dispatches to one of six upserter services (UpsertPatientAllergyService, UpsertPatientMedicationService, UpsertPatientConditionService, etc.). Upserters dedupe against existing chart rows by canonical concept ID — so re-submitting "Penicillin" on a future encounter doesn't create a duplicate row.

Encounter answers (tier 3 + chart-sync)

Free-form key/value object keyed by field slug. Values are persisted in tier3_encounter_questions JSON AND as individual encounter_intake_answers rows (one per slug). For slugs that map to standard chart fields (e.g. current_weight_lbs) the answer also flows through IntakeAnswerRouter to the chart. tier 3chart-sync

Discover slugs: GET /api/v1/telehealth/encounter-types/{id}/schema returns the canonical list of fields + types + display conditions for an encounter type.

ApiIntakeDependencyValidator runs after the basic schema validation and enforces conditional required rules (e.g., a follow-up answer required when a parent answer is "Yes"). Failures return 422 with field-level error messages.

Payment block

Five modes — pick exactly one. Sales-org and client tokens cannot use authorize (PRX is not the merchant of record on API flows).

payment.modeRequired fieldsOrder outcome
authorizegateway, amount, card_tokenPRX runs pre-auth. Order workflow → READY_FOR_CAPTURE. Embed-only.
reference_preauthpre_auth.transaction_id, pre_auth.authorized_amountYou ran a pre-auth; we record + vault. Capture later via POST /orders/{id}/capture.
reference_capturedtransaction.transaction_id, transaction.amountRecord-only audit trail of a sale you already ran.
prepaidreasonNo charge — out-of-band billing settled. Order workflow → READY_FOR_FULFILLMENT.
patient_review— (no extra fields)Defer — patient gets emailed a portal link to confirm + pay.

payment.gateway in authorize mode must be one of authorize_net / stripe / nmi / square. In record-only modes, it accepts any free-form string (the integrator's gateway name, recorded for audit).

Tip — confirming where your data landed. After a successful intake, GET /api/v1/encounters/{id}?include=patient,prescriptions,soapNotes returns the full encounter + chart-side rows that resulted from the upsert pipeline. Use this to verify medications/allergies/conditions were matched to terminology rows (vs. persisted as free-text), and to confirm the encounter status transitioned correctly.
